Lakehouse pipeline

A CSV pipeline that validates the input contract, handles duplicates, quarantines invalid records and publishes a SQL analytics layer.

This study uses synthetic data. I ran and tested the Python/SQLite pipeline locally and executed the full PySpark/Delta notebook in GitHub Actions. The Databricks workspace run is pending.

Input rows 670
Valid orders 600
Quarantined rows 70
Automated tests 4

Problem and solution

Sales files can contain duplicates, invalid dates and inconsistent values that distort KPIs. The pipeline validates each row before publishing it for analysis and records why each row was rejected.

Synthetic CSV → schema contract → validation and deduplication
├── quarantine.csv with reasons
└── fact_sales (SQLite)
    ├── monthly SQL aggregation
    ├── CSV for Power BI
    └── JSON for the dashboard

Reproduce the results

git clone https://github.com/GabrielCosta06/portfolio-data-analyst.git
cd portfolio-data-analyst
python src/pipeline.py --generate
python -m unittest discover -s tests -v
python -m http.server 8080

Open http://localhost:8080. The local pipeline requires Python 3.10+ and uses the standard library. Each run replaces the demonstration analytics layer to avoid duplicate orders.

Technical decisions

  • Each row represents one order. Deduplication keeps the first valid record. Production systems need an update rule for conflicting records.
  • The pipeline calculates financial values with Decimal and stores them as integer cents.
  • Input schema changes stop execution before the pipeline replaces the previous output.
  • The manifest records the input SHA-256 hash, counts, failures and aggregates for reconciliation.
  • All exports come from the same accepted synthetic records.

Scope and next steps

This is an in-memory batch pipeline. A production implementation would need to specify and validate change data capture, streaming, network retries, scheduling, authentication and transaction recovery across related outputs.

The verified run uses local Spark on a GitHub runner. Verification in a Databricks workspace and deployment to AWS or Azure are outside the verified run.
